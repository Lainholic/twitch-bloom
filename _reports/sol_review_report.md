환님, **군중 제어 우려가 타당합니다. `ㅋㅋ` 감지 범위부터 넓히는 것은 권하지 않습니다.** 다만 현재 코드에서 웃음은 쓰레기를 새로 만드는 동작이 아니라, **이미 있는 쓰레기 전체를 다시 튀게 하는 동작**입니다. 대규모 채팅에서는 소품 개수 폭증보다 **반복적인 전체 흔들림·낙하·파티클 재생**이 직접적인 문제입니다.

또한 애니 리포트에는 **제공된 현재 코드에 없는 `new Map()` 렌더 루프와 픽셀 클러스터 계산을 실제 결함처럼 인용한 부분**이 있습니다. 해당 근거부터 바로잡아야 합니다.

## 3. 환님의 핵심 질문: “사람이 많으면 정신없지 않은가?”

### 3.1 실제 코드가 하는 일

`garden.mjs → apply()`:

```javascript
// Laugh reaction (no cooldown, just visual/audio bounce)
if (command === 'laugh') {
  return { accepted: true, command: 'laugh', owner };
}

// Check cooldown
const u = stats.userActions.get(owner);
```

**웃음 분기가 사용자 쿨다운보다 앞에 있습니다.** 중복 ID가 아닌 웃음 메시지는 같은 사용자가 반복해도 받아들입니다.

`renderer.mjs → triggerLaughEffect()`의 함수 내 상대 행:

```javascript
1  function triggerLaughEffect() {
2    for (const record of flowersMap.values()) record.jiggle = 0.45;
3    for (const item of activeTrashList) {
4      item.vy = -180 - Math.random() * 120;
5      item.vRot = (Math.random() - 0.5) * 8.0;
6      item.isResting = false;
7      item.bounceCount = 0;
8    }
```

이어지는 반복문은 하트 파티클 20개를 생성합니다.

따라서 웃음 한 번은:

- 꽃 전체 흔들림 재설정
- 쓰레기 전체에 상승 속도 부여
- 정지 상태 해제
- 바운스 횟수 초기화
- 파티클 20개 생성

을 수행합니다.

**새 쓰레기 생성은 없습니다.** 하지만 이 효과가 입력마다 연결된다면, 많은 웃음 메시지에 쓰레기들이 계속 재발사되어 안정적으로 착지하기 어렵습니다. 실제 연결부가 없으므로 “메시지마다 효과 호출”은 아직 확인하지 못한 조건입니다.

### 3.2 개수 제한과 생성률 제한은 다릅니다

현재 기본 `trashCapacity = 100`은 저장된 쓰레기 개수를 제한합니다.

```javascript
if (trashItems.length >= trashCapacity) trashItems.shift();
trashItems.push(trash);
```

하지만 **100개가 찬 후 새 쓰레기가 들어오는 속도**는 제한하지 않습니다. 오래된 것을 버리고 새것을 만드는 교체가 계속됩니다.

꽃도 기본 150개로 제한되지만, 다수의 새로운 사용자가 동시에 참여하는 생성률은 제한하지 않습니다.

결론:

> **현재 하드캡은 메모리의 일부를 제한할 뿐, 화면의 정신없음과 입력 처리 비용을 제한하지 않습니다.**

### 3.3 권장 방어 설계

핵심은 **채팅을 개별 물체로 바꾸지 않고, 집단 반응의 강도로 집계하는 것**입니다.

아래 수치는 벤치마크 결과가 아닌 **보수적인 초기 튜닝값**입니다.

| 제어 항목 | 대형 방송 초기값 | 정책 |
|---|---:|---|
| 사용자별 쓰레기 생성 | 5초당 1회 | 동일 사용자의 반복 투척 차단 |
| 전역 쓰레기 생성 | 초당 2개, 버스트 3개 | 토큰 버킷 적용 |
| 전체 쓰레기 | 40개 | 가득 차면 기본적으로 신규 투척 거절 |
| 동시 낙하 쓰레기 | 6개 | 렌더러에서 별도 제한 |
| 사용자별 웃음 집계 | 2초당 1회 | 집계 기여도 제한 |
| 웃음 집계 창 | 500ms | 메시지마다 효과 호출 금지 |
| 웃음 효과 전역 간격 | 최소 2초 | 집계 결과도 쿨다운 적용 |
| 일반 효과 재생 예산 | 초당 3회, 버스트 3회 | 물·햇빛·청소가 공유 |
| 파티클 | 최대 120개 | 가득 차면 신규 생성 생략 |
| 이름표 | 동시 12개 이하 또는 기본 OFF | 밀집·텍스트 가림 방지 |

**웃음 티어링 예시:**

- 500ms 동안 고유 사용자 3~9명: 꽃만 약하게 흔들기
- 10~29명: 꽃과 소수 쓰레기만 약하게 반응
- 30명 이상: 강도를 더 키우지 않고 짧은 집단 반응 표시
- 어떤 티어에서도 전체 쓰레기 재발사 금지

채널 규모별로 임계값은 조정하되, **최대 강도는 고정**해야 합니다.

화면 중앙 보호도 별도 정책으로 둡니다.

- 쓰레기 낙하는 하단 15%에서 시작
- 얼굴·게임 HUD 영역을 제외 구역으로 설정
- 넝쿨 최대 성장·불투명도·표시 영역 제한
- 스트리머용 즉시 정지/효과 비활성화 제공

**`ㅋㅋ`는 나중에 넓혀도 됩니다. 먼저 집계와 예산을 넣는 것이 순서입니다.**

### 정규화 슬롯 제안의 평가

해상도 독립적인 슬롯은 유용합니다. 다만 애니의 제안처럼 `layer`를 영구 부여하는 것만으로는 다음 문제가 해결되지 않습니다.

- 삭제·FIFO 퇴출 후 슬롯 점유 해제
- 중간층 제거 후 재정착
- 슬롯 높이 상한 초과 정책
- 낙하 중 물체의 예약과 취소
- 웃음으로 다시 움직이는 물체 처리

또한 `Math.round(item.x * 25)`는 주어진 좌표 범위에서 대략 **45개 슬롯**이며, 예시 주석의 “40개”와 일치하지 않습니다.

**해커톤에서는 물리 전체 이관보다, 슬롯·점유 정책만 논리 계층에서 고정하고 시각 보간은 렌더러에 유지하는 편이 현실적입니다.**

## 5. 실제 코드의 숨은 결함

### 5.1 사용자 기록은 무한 증가한다 — P0

`garden.mjs → trackUser()`:

```javascript
if (!stats.userActions.has(user)) {
  stats.userActions.set(user, { ... });
}
```

사용자를 삭제하거나 상한을 적용하는 코드가 없습니다. 꽃이 FIFO로 삭제되어도 기록은 남습니다.

`getMVPs()`는 누적 사용자 전체를 복사하고 두 번 정렬하며, `getStats()`는 `topUsers`를 위해 또 정렬합니다.

- 사용자 기록 공간: 고유 사용자 수에 비례
- 통계 조회 비용: 대략 `O(U log U)`
- 매 프레임 호출된다면 특히 위험하지만, 호출 주기는 미제공입니다.

**대응:** 사용자 기록 상한·TTL, 쿨다운 저장소 분리, 통계 캐시. 정렬 대신 상위 1명·5명만 찾는 방식도 가능하지만 저장 상한 자체가 먼저입니다.

### 5.2 “불변 스냅샷”은 부분적으로만 성립한다 — P1

```javascript
list.stats = { ...stats, ... };
```

여기서 `stats.userActions`는 내부 Map 그대로입니다.

```javascript
getFlowers: () => [...flowers.values()].map(f => ({ ...f }))
```

`traits`는 중첩 참조가 유지됩니다.

또한 `apply()`는 내부 `flower` 또는 `trash` 객체를 그대로 반환하고, `getStats().topUsers`도 내부 사용자 기록 객체를 반환합니다.

**외부 호출자가 반환 객체를 수정하여 내부 상태를 바꿀 수 있습니다.** 외부 공격 경로가 확인된 것은 아니지만, 첫 주석의 상태 소유권 계약과 맞지 않습니다.

**대응:** 반환 DTO를 복사하고 중첩 객체·Map도 분리합니다. 테스트는 `snapshot()[0].traits` 한 경로만 검사하고 있어 이 결함을 잡지 못합니다.

### 5.3 리사이즈 시 기존 객체 위치가 고착된다 — P1

리사이즈 핸들러는 `width`, `height`, 캔버스 크기만 변경합니다.

`syncFlowers()`에서는 새 목표 위치를 계산하지만 **기존 record에 `x`, `y`를 갱신하지 않습니다.**

`syncTrash()`도 기존 record에 새로운 화면 좌표·바닥 목표를 적용하지 않습니다.

따라서 실제 문제는 애니가 주장한 “클러스터 재분류”가 아니라:

- 꽃이 옛 좌표에 남음
- 쓰레기 바닥 목표가 옛 화면 높이에 남음
- 화면 축소 시 객체가 화면 밖에 위치할 가능성

입니다.

아울러:

```javascript
setSize: (w, h) => {
  canvas.width = w;
  canvas.height = h;
  ctx.imageSmoothingEnabled = false;
}
```

이 함수는 클로저의 `width`, `height`를 갱신하지 않아 렌더 계산과 실제 캔버스 크기가 불일치합니다.

**OBS의 장면 변환으로 소스를 확대·축소하는 것과 브라우저 viewport 자체를 변경하는 것은 구분해야 합니다.**

### 5.4 현재 적재는 안정적인 5층 슬롯 물리가 아니다 — P1

적재 검사:

```javascript
if (other.isResting && Math.abs(other.x - posX) < 22)
```

낙하 중 물체는 무시합니다. 동시에 생성된 여러 물체는 같은 바닥 목표를 가질 수 있습니다.

또한 생성 후 `vx`로 수평 이동하지만 적재 목표는 다시 계산하지 않습니다. 출발 위치에서 결정한 층이 최종 착지 위치의 이웃 관계와 달라질 수 있습니다.

청소 침하는 이미 존재합니다.

```javascript
above.targetY = Math.min(floorY - 14, above.targetY + 11);
above.isResting = false;
above.vy = 50;
```

그러나 지원 관계나 슬롯 점유 없이 근접 조건으로 처리하므로 복잡한 더미에서 정확한 재정착을 보장하지 않습니다.

**방송 장식이라면 완전한 물리 엔진은 불필요합니다.** 고정 슬롯과 제한된 층수, 간단한 보간이면 충분합니다.

### 5.5 실제 렌더 할당 비용은 다른 곳에 있다 — P1

현재 `renderFrame()`은 넝쿨 배열 세 개와 **총 48개 설정 객체**를 호출마다 만듭니다.

또한:

- 꽃마다 이름표 `measureText()` 호출
- 황금 꽃마다 프레임 기반 확률로 파티클 생성
- 파티클 삭제에 `splice()`
- 포화 상태 파티클 생성에 `shift()`

이 있습니다.

특히 황금 꽃 파티클은 초당 발생량이 FPS에 비례합니다. **효과 발생을 시간 기반으로 전환**해야 합니다.

`spawnParticle()`:

```javascript
if (particles.length > 180) particles.shift();
particles.push(...);
```

실제 최대 길이는 정상 경로에서 **181개**입니다. 또한 상한이 있어도 지속적인 객체 생성 비용까지 사라지는 것은 아닙니다.

`triggerGoldEffect()`의 `fireflies.push()`에는 개수 상한이 없습니다. 현재 `gold` 명령은 도달 불가지만, 다른 호출 경로까지 안전하다고 볼 수는 없습니다.

### 5.6 IRC는 기본 방어가 있으나 운영 오류 처리가 거칠다 — P1

긍정적인 부분:

- 채널·인증 입력 검증
- TLS WebSocket
- 채널 필터
- 메시지 단편 처리
- 버퍼 상한
- PING/PONG
- 지수 백오프와 jitter
- 오래된 socket 메시지 차단

문제 부분:

```javascript
if (message.command === 'NOTICE' || ...)
```

**모든 NOTICE를 영구 거절로 취급**합니다. NOTICE 전체가 인증 실패라는 보장은 없습니다. 식별 가능한 인증·입장 거절만 중단하고, 일반 안내는 상태로 처리하는 편이 안전합니다.

추가로:

- IRC 태그 escape 해제 없음
- `onChat` 예외 격리 없음
- 한 WebSocket 이벤트의 모든 줄을 동기 처리
- 프레임 처리량과 미완성 잔여 버퍼를 합쳐 64KiB 제한

이 있습니다. 마지막 항목은 방어 효과가 있지만 정상 큰 배치도 닫을 수 있으므로 정책을 분리하는 것이 좋습니다.

### 5.7 파서·설정의 추가 결함 — P1/P2

- `/lol|lul|lmao/i`는 `lollipop` 같은 단어 내부도 매칭합니다.
- 이모지 조건이 명시 명령과 같은 분기에 있어 `!clean 💧`가 `water`로 처리됩니다.
- `gold`는 파서에서 `trash`로 분류되므로 `command === 'gold'` 분기는 도달 불가입니다.
- `autoPlant` 옵션은 사용되지 않습니다.
- `capacity`, `trashCapacity`, `cooldownMs`의 유효성 검사가 없습니다. `NaN`·`Infinity` 등의 설정은 상한 정책을 무력화할 수 있습니다.

## 6. 즉시 수정할 P0 핀셋 패치 가이드

### P0-A. 웃음 직접 재생을 집계로 교체

**수정 대상:** `garden.apply()` 웃음 분기와 이벤트 연결부.

1. 사용자별 웃음 기여 쿨다운 검사
2. 500ms 고유 사용자 집계
3. 집계만 업데이트하고 직접 재생하지 않음
4. 전역 2초 간격으로 최대 1회 효과 재생
5. `triggerLaughEffect()`에서 전체 쓰레기 재발사 제거

의미 구분 예시:

```javascript
// 설계안: 상태 반영과 시각 효과 재생을 구분
{
  accepted: true,
  command: 'laugh',
  counted: true,
  emitEffect: false
}
```

집계기·타이머는 Garden 인스턴스 또는 컨트롤러별로 소유해야 합니다. 모듈 전역 싱글톤은 피합니다.

### P0-B. 전역 생성 예산과 포화 정책 추가

**수정 대상:** `trash` 분기의 생성 직전.

```javascript
// 의사코드 — 그대로 적용 가능한 완성 패치 아님
if (!trashBudget.tryConsume(now)) {
  return { accepted: false, reason: 'global-rate' };
}
if (trashItems.length >= trashCapacity) {
  return { accepted: false, reason: 'capacity' };
}
```

- 전역 예산은 사용자별 제한과 함께 적용
- 물·햇빛의 상태 반영과 대형 시각 효과 재생을 분리
- 포화 상태에서 삭제·생성을 계속 반복하지 않음
- 입력 큐는 길이와 TTL 모두 제한

### P0-C. 장기 저장소와 모든 효과에 하드캡

- `userActions`: 검증 가능한 상한과 만료 정책
- 웃음 집계용 Set: 집계 창 종료 시 폐기, 창 내 상한 적용
- 파티클: `>= cap`이면 생성 생략
- fireflies: 별도 상한
- 이름표·동시 낙하 수 제한
- 설정값에 유한 정수·허용 범위 검사

**이 세 항목이 Map 재사용이나 `ㅋㅋ` 정규식 변경보다 먼저입니다.**

## 7. 출시 전 필수 검증

현재 테스트는 기본 규칙 확인에는 유용하지만, 다음을 입증하지 못합니다.

| 추가 검증 | 합격 조건 |
|---|---|
| 1초에 고유 사용자 1,000명 웃음 | 집계만 증가, 효과는 전역 간격 준수 |
| 동일 사용자 웃음 반복 | 창별 기여 제한 준수 |
| 대량 투척 | 생성 예산·전체 개수·동시 낙하 상한 준수 |
| 누적 고유 사용자 증가 | 사용자 기록 상한 유지 |
| 포화 상태 도배 | 큐·파티클·교체 처리량이 제한됨 |
| 모든 공개 반환값 변조 | Garden 내부 상태 변경 없음 |
| viewport 변경 및 `setSize()` | 바닥·꽃·쓰레기 좌표 일관성 유지 |
| 일반 NOTICE / 인증 실패 / RECONNECT | 각각 올바른 상태 전이 |
| OBS 실제 실행 | 목표 FPS·렌더 시간·화면 가림 실측 |
| 장기 실행 | GC 이후 힙 기준선의 지속 상승 여부 확인 |

OBS 평가는 평균 FPS만 보지 말고 프레임 시간 p95/p99, 긴 작업, 활성 객체 수, 입력 지연을 함께 기록해야 합니다. 현재 자료만으로 구체적인 FPS 보장은 할 수 없습니다.

## 8. 최종 총평

환님께 권하는 방향은 명확합니다.

> **“시청자 한 명의 채팅 = 소품 한 번”이 아니라, “여러 시청자의 반응 = 제한된 집단 연출 한 번”으로 바꾸십시오.**

애니가 맞게 짚은 것은 이모지 오작동 가능성, 해상도 독립적인 배치 필요성, 렌더러 회귀 테스트 부재입니다. 반면 **현재 코드에 없는 Map 문제, GC 제로 주장, 두 수정만으로 수천 명 방송 보장**은 채택 근거로 쓰기 어렵습니다.

**해커톤은 군중 제어 P0 적용 후 CONDITIONAL GO, 대규모 공개 방송은 현재 NO-GO**입니다. 핵심 예산·집계·하드캡을 넣고 실제 OBS 부하 검증을 통과하면 재평가할 수 있습니다.
